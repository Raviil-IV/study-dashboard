# Дизайн-спецификация: Админ-панель со статистикой и ролями

Дата: 2026-08-11
Проект: Study Dashboard (React 19 + Vite 7 + TS + Zustand + Tailwind v4, backend Express + Drizzle + PostgreSQL)
Статус: черновик (на ревью)

## 1. Цель

Добавить в Study Dashboard административную панель со статистикой по платформе и по отдельным пользователям. Доступ к панели — только для пользователей с ролью `admin`. Роль хранится в таблице `users` и выдаётся/отзывается администратором через ту же панель (список пользователей + смена роли). Первому администратору роль назначается вручную в БД.

## 2. Принятые решения

- **Роль в БД**: новая колонка `role` в таблице `users`, тип `text` с enum `user | admin`, default `user`. Никакой отдельной таблицы ролей (одна роль на пользователя, YAGNI).
- **Источник истины о роли — БД**: middleware `requireAdmin` читает роль из БД на каждый запрос (админ-запросы редкие, стоимость неважна). Смена роли применяется мгновенно, без ожидания истечения JWT.
- **Роль в ответах авторизации**: `/api/auth/me`, `login`, `register` возвращают `{ id, login, role }`, чтобы фронтенд знал роль после входа.
- **Первый админ — вручную**: SQL `UPDATE users SET role = 'admin' WHERE login = '...'`. Программного способа «назначить первого админа из интерфейса» нет (никто не админ → некому).
- **Защита от само-понижения**: админ не может сменить роль самому себе (иначе можно случайно «запереть» платформу).
- **Агрегация — в PostgreSQL**: статистика считается SQL-запросами (`count`, `sum`, `group by`, оконные функции не нужны), а не выборкой сырых строк в Node.
- **График — самописный SVG** без новых зависимостей: в проекте нет библиотек графиков, тянуть recharts ради двух графиков нецелесообразно.
- **Ошибки**: доступ не-админа — `403 FORBIDDEN`; на фронте — тост и редирект на дашборд.

## 3. Метрики

### 3.1 Глобальная сводка (`GET /api/admin/stats`)

| Группа | Метрика | Источник |
|---|---|---|
| Пользователи | всего зарегистрировано | `users` |
| Пользователи | новых за последние 7 дней | `users.created_at` |
| Пользователи | новых за последние 30 дней | `users.created_at` |
| Активность | активных за 7 дней (есть завершённая фокус-сессия за период ИЛИ задача с created_at/completed_at за период) | `focus_sessions`, `tasks` |
| Активность | активных за 30 дней | то же |
| Фокус | суммарно минут за 7 дней | `focus_sessions.duration_minutes` (completed) |
| Фокус | суммарно минут за 30 дней | то же |
| Фокус | средняя длительность сессии (всего) | то же |
| Задачи | всего создано | `tasks` |
| Задачи | выполнено, % выполнения | `tasks.status = 'done'` |
| Задачи | просрочено (due_date < сегодня, status ≠ done) | `tasks` |
| Дедлайны | в ближайшие 7 дней | `deadlines.date` |
| Дедлайны | пропущенные (date < сегодня) | `deadlines` |
| Заметки | всего, среднее на пользователя | `notes` / `users` |
| Тренд | фокус-минуты и выполненные задачи по дням за 30 дней | `focus_sessions`, `tasks.completed_at` |

### 3.2 Метрики пользователя (`GET /api/admin/users/:id/stats`)

- Мини-профиль: логин, роль, дата регистрации.
- Фокус: всего сессий, всего минут, за 30 дней минут.
- Задачи: всего, выполнено, в работе (`in-progress`), просрочено.
- Дедлайны: предстоящие, пропущенные.
- Заметки: всего.
- Игры: лучшие рекорды по играм/сложностям.
- Активность по дням за 30 дней (фокус-минуты + выполненные задачи) — для графика.

## 4. Модель данных

Изменение в существующей таблице:

| Таблица | Колонка | Изменение |
|---|---|---|
| `users` | `role text ('user'\|'admin') not null default 'user'` | новая колонка |

Миграция: `drizzle-kit generate` (файл миграции в репозитории, применяется при старте backend автоматически, как существующие).

## 5. API

Новый роут `admin.ts`, монтируется в `app.ts` под `requireAdmin`:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/admin/users` | список пользователей: `id`, `login`, `role`, `created_at`, число задач и фокус-сессий (для таблицы) |
| `PATCH` | `/api/admin/users/:id/role` | `{ role: 'user' \| 'admin' }` — смена роли; `403`, если `:id` === текущий админ |
| `GET` | `/api/admin/stats` | глобальная сводка + тренд за 30 дней (см. 3.1) |
| `GET` | `/api/admin/users/:id/stats` | метрики пользователя (см. 3.2) |

Схемы zod: `roleParamSchema` (`enum(['user','admin'])`), `userIdParamSchema` (`z.string().uuid()`).

Middleware: `requireAdmin` — поверх `requireAuth`, делает `SELECT role FROM users WHERE id = req.userId`; роль не `admin` → `403 { code: 'FORBIDDEN' }`.

## 6. Фронтенд

### 6.1 Типы и стора

- Тип `User` в `src/types`: добавляется `role: 'user' | 'admin'`.
- `useAuth`: `user` содержит `role` (приходит из `/auth/me`, `login`, `register`).
- Хранилище не меняется: админ-данные не в Zustand, фетчатся на странице.

### 6.2 Роутинг и доступ

- `App.tsx`: новый маршрут `admin` под `AppLayout`.
- Новый компонент `AdminRoute` (аналог `ProtectedRoute`): если `user.role !== 'admin'` → редирект на `/` (и тост «Нет доступа»).
- `AppLayout`: пункт меню «Админка» виден только при `user.role === 'admin'`.

### 6.3 Страница `/admin`

Компоненты:
- `AdminPage` — общий layout страницы, загрузка данных, переключение «Сводка / Пользователи».
- `StatsCards` — карточки глобальной сводки (пользователи, активность, фокус, задачи, дедлайны, заметки).
- `ActivityChart` — самописный SVG-график: две серии (фокус-минуты, выполненные задачи) по дням за 30 дней; используется в сводке и в профиле пользователя.
- `UsersTable` — таблица пользователей: логин, роль (select или кнопка переключения), дата регистрации, число задач/сессий, кнопка «Открыть» → профиль пользователя.
- `UserStats` — блок метрик выбранного пользователя + его график + кнопка назад.
- `RoleBadge` — небольшой бейдж роли.

Состояние страницы: локальный `useState` (загрузка, ошибки, выбранный пользователь), без новых зависимостей.

### 6.4 Обработка ошибок

- `403` → тост + редирект на дашборд.
- Сетевые ошибки → тост (существующий `notifyError`) + повторная попытка кнопкой «Обновить».

## 7. Тесты

- **Backend** (Vitest + Supertest, в `backend/test`):
  - `requireAdmin`: без куки — 401; с кукой не-админа — 403; с кукой админа — проходит.
  - `PATCH role`: смена роли другому пользователю — 200 и роль изменилась в БД; смена самому себе — 403; невалидная роль — 400.
  - `GET /api/admin/users`, `GET /api/admin/stats`, `GET /api/admin/users/:id/stats` — 200 для админа, 403 для не-админа.
- **Frontend** (Vitest + Testing Library):
  - `AdminRoute`: редирект не-админа на дашборд; пропуск админа.
  - `AppLayout`: пункт «Админка» виден админу, скрыт обычному пользователю.
  - `AdminPage`: рендерит карточки статистики после успешной загрузки; при `403` — тост и редирект.
  - `ActivityChart`: рендерит SVG с точками/столбцами по данным.

  ## 8. Вне объёма

  - Удаление пользователей и их данных из панели.
  - Просмотр содержимого заметок/задач пользователей.
  - Аудит-лог действий администратора.
  - Публичная «доска лидеров» по играм.
  - Уведомления администратору о новых регистрациях.
